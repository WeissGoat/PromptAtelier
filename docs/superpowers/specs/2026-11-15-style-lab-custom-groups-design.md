# Style Lab 自定义分组与两阶段 Agent 流程

日期：2026-11-15

状态：已实现自定义分组、准备接口、测试快照计划与两阶段 skill。下文保留设计依据与验收要求。

## 目标与边界

把目前的 Agent 全流程拆成两个独立入口：

1. **准备**：输入图片/文件夹 → 创建或复用工作区 → 分析 → 保存自定义分组 → 挑代表图 → 划分并建立配方。到此结束，所有新配方标为「待测试」。
2. **测试**：用户指定分组或配方 → 形成明确的样本清单 → 原参重生 → 配方原图内容测试 → 当前角色/动作测试。

第一步不提交任何图片生成，包括原参重生。第二步只执行用户指定的对象，不从「分析完成」自动进入测试。

本轮按现有 Agent 操作 Web API 的方式设计：用户在聊天里给路径和要求，Agent 完成分析并写回；Web 提供可持久编辑的分组、配方复核和测试选择。Web 新建工作区仍能独立使用，尚未经过 Agent 分析时显示「未建立自定义分组」，不会假装已运行完整分析。无需新增常驻 Agent 服务。

## 现状与需要修正的耦合

- `GroupPanel.tsx` 目前支持画风、投稿、月份。画风来自 `/analysis` 的计算结果，不能保存人工改名、合并、成员调整或分析依据。
- `grouping.py` 按投稿聚类，已有画师/风格栈、稳定变体、vibe 与模型分组，可作为分析素材。家族 id 为排序产生的 `g1/g2/...`，重扫或分类结果改变后可能指向另一组。
- 配方的 `group_id` 目前只指自动组；前端同组共性、后端回归图片挑选都直接按它查自动分析结果。不能把自定义组 id 填进去却仍按自动组解析。
- 当前 `style-lab` skill 默认建配方后继续出图，并通过临时保存内容变体再恢复基准来做素材测试。新流程需要明确阶段边界；批量测试应保存独立快照，减少对编辑器的干扰。

## Web 分组设计

分组栏增加常驻切换：`自定义 / 自动画风 / 投稿 / 月份`。自定义与自动画风是两套视图；投稿/月分类只在有相应信息时显示。自定义视图对散图也始终可用，不能沿用当前「无投稿则强制 style」的逻辑。

自定义分组由用户和 Agent 共用，Agent 分析后的分组可以继续人工修改。初版只支持「画风家族 → 子组」两级，避免任意深度目录。

```text
自定义分组
  清晰漫画线条                  28 投稿 / 76 图
    基础栈 · 无 vibe · NAI4.5    19 投稿 / 51 图   配方 1
    加权画师变体 · vibe A         9 投稿 / 25 图   配方 2
  柔和上色                      12 投稿 / 34 图
    无 vibe · NAI5              10 投稿 / 27 图   配方 1
    缺参考图                     2 投稿 /  7 图   需处理
  特殊来源归档                    3 投稿 /  8 图
  待判断                          1 投稿 /  2 图
  未分组                          5 投稿 / 13 图
```

组名用简短风格描述；模型、vibe、参数细节主要通过子组与徽标展示。不能仅凭「柔和」「漫画」等词名就推断已满足稳定分组条件。

每组提供：改名、备注、排序、调整父组、合并、拆分、成员增删、指定代表图、打开关联配方。图片支持多选后「移到自定义组」；投稿视图支持整投稿操作。可将现有自动组的当前成员复制为一个自定义组，保存的是成员快照及来源依据。

点击组筛选图库和共性分析；配方列表可按组过滤。组详情展示：

- 主画师/风格组合、稳定变体及差异依据。
- 投稿数、图片数、日期范围、在整个工作区的投稿占比。
- 可用文生图数量、vibe/缺参考图/特殊来源情况。
- 代表图、相关配方、准备状态与测试结果。
- 分析者（Agent/用户）、简短判断理由、证据图片、最后分析时间。

### 成员与统计

- 自定义组 id 使用稳定 UUID，不从名字、排序或自动组 id 推导。改名、重扫不换 id。
- 图片在自定义视图中最多有一个主要叶子组；父组成员由子组汇总。未分配的图片进入「未分组」。自动视图中的归属不受影响。
- 默认按整投稿归组；同投稿内确有不同风格/可恢复性时允许明确拆图，记录原因。组统计按原投稿去重，父级/工作区不能相加子组数字代替去重统计；散图各算一个来源单位。
- 作为证据或抢救样本的跨组引用单独记录，不能重复计入归属或投稿数。同一原图不会因展示在多个证据面板而多算。
- 「缺参考图」「特殊来源」是可恢复性标记，有风格依据的仍放在对应家族下；真正不能归类的进入待判断。整投稿仅 img2img/inpaint 且无可恢复 vibe 的归档可放顶层。

## 迁移 artist-style-reproduction 的分析经验

来源：`F:/my_project/agent-hub/skills/artist-style-reproduction/SKILL.md` 与 `references/grouping-rules.md`。实施时将适配后的分析规则放进本项目 skill 的 `references/analysis-rules.md`，不要求执行时依赖该外部绝对路径。

| 经验 | 在本项目的适配 |
|---|---|
| 先恢复/读取元数据再分析 | 使用现有 PNG 文本和 stealth 读取器，记录来源。保持源图只读，不搬迁旧 skill 的回写流程 |
| 原图证据优先 | 使用直接读取图片产生、按 path/size/mtime 失效的索引与缓存。旧 CSV、sidecar 只作线索，不当作事实 |
| 按投稿统计 | 同投稿多图不放大风格频率；记录占比、时间跨度和近期稳定性 |
| 组合优先于单词频率 | 综合画师栈、权重、风格组合、跨投稿稳定性，不只看某个高频 tag |
| 主类要粗 | 先识别稳定画风家族，再区分 vibe 状态、模型和有证据的变体 |
| 不过度拆分 | 分辨率、种子不分风格；steps/CFG/sampler 等通常作为参数变体；质量词、光影和一次性调味词不单独升主类 |
| 稳定漫画/单色等变体 | 跨投稿确有稳定画师栈/视觉证据才拆；内容、动作词不混入风格区 |
| 识别缺失参考素材 | 有 vibe 参数但无内嵌图不能叫无 vibe；整体缺参考的投稿在对应家族中标记待处理 |
| 处理混合投稿 | 同投稿部分图可恢复 vibe 时保留共享分组，缺失图单列问题；特殊图片不导致整投稿一律丢弃 |
| 抢救可用普通图 | 正常文生图、无内嵌 vibe 且无 vibe 参数的图可成为替代样本，记录原来源，不复制目录、不增加投稿统计 |
| 特殊来源归档 | 全投稿 img2img/inpaint、无可恢复 vibe 时归档；有可恢复 vibe 时保留风格/vibe 归属，同时标记缺底图限制 |
| 待判断要有依据 | 不能有证据还长期挂 unknown；确实无法判断的写出原因，不能编造归属 |
| 优先选稳定版本 | 综合投稿占比、近期连续性、参数/提示词稳定性及可复现性；优先主流家族中较新且可用的代表图，不机械选最新一张 |
| 校验归组一致性 | 将旧目录校验转换为图片 id、成员唯一性、引用、投稿去重、vibe 语义校验；不直接运行依赖旧目录结构的 validator |

采用证据强度 `充分 / 有限 / 待判断` 和文字理由，不生成缺少依据的精确置信百分数。自动聚类是候选依据，Agent 可以合并、修正，必须留下理由。

## 第一步：导入、分析、分组与配方

1. 输入一组图片或若干文件夹；沿用现有规则建立/复用一个或多个工作区，索引源图。
2. 输出按投稿分段的分析上下文：完整风格栈、参数摘要、vibe hash/状态、日期、特殊标记和候选图。大图库分页读取，不一次塞入所有元数据。
3. Agent 按适配规则分析，形成组、成员、证据、特殊情况和代表图的结构化结果，并给出简短报告。
4. 校验并保存为自定义分组。用户手动编辑过的组/归属支持锁定；重新分析保留锁定项，变化作为建议，不直接覆盖。
5. 对可建立配方的子组，从代表源图创建并完成画风划分、预览与保存。默认每个可用子组一份，稳定差异确实需要多份时分别建。一个组可关联多个配方，不能把组和配方做成一对一。
6. 配方保留原图内容、完整角色 captions、负面、模型、vibe 与参数；画风区锁定，状态为「待测试」。初始全放 subject 的空划分草稿不算已准备好。
7. 输出工作区/自定义组/配方清单、分析理由、可测试项与待处理项，到此结束。

缺参考、特殊来源或证据不足的组也要保存，可留待处理或建明确标记的草稿，但不能显示「可正常测试」。准备阶段不读取并固化用户角色/动作选择，这些在测试阶段获取。

### 状态

复用现有 `stage=split/edit` 与 `locked` 表示配方编辑阶段。另加准备信息，不把「编辑中」「分析完成」「出图成功」混成一个枚举：

- `preparation.status`：`needs_review / ready / stale / source_missing`。
- 测试状态从测试计划与 run 派生：`untested / queued / running / succeeded / partial / failed / interrupted`，并展示覆盖范围。
- `ready` 只代表可以开始测试。原参、配方原图、素材测试各自记录结果，不能一张成功就标全部通过。

## 第二步：用户指定后测试

入口支持明确配方 id，或选中自定义组后展开其配方。选父组时展示实际包含哪些叶子组/配方；按 id 去重。待处理配方列明原因，不静默混入任务。

聊天示例：

```text
$style-lab 测试工作区「作者A」里的「清晰漫画线条」组，
只测配方 r_a1、r_a2；每份测试当前素材架里的 3 个不同角色/动作组合。
```

Web 中勾选配方后，测试面板展示范围、当前素材和 exclusions、代表源图、种子/尺寸、预计新生成/可复用/跳过张数，以及已准备好的变体预览；点击「开始测试」即提交。聊天里用户已经明确要求测试时，Agent 给出同样的摘要并直接执行，无需再次确认。

默认每个选定配方：

1. 代表源图原参重生 1 张，同一源图被多个配方使用时共享一次有效结果。
2. 配方保留原图内容测试 1 张。
3. 用户当前选择的角色和动作，最多 3 个不同组合、每组合 1 张。用户指定数量/组合则按指定范围。

全部沿用各自原图的种子和生成尺寸，不用 `count>1` 代替不同内容，避免种子自动递增。素材架在计划创建时读取一次并保存完整快照；执行中选择变化只影响下一次计划。两类素材均为空时只执行前两项并说明。

原参失败先停止受影响源图的后续测试；参数差异或漂移需要记录诊断，再决定是否继续该源图。其余独立源图可继续，批次结果可为 partial。正常配方图的 `verdict=reference` 不当作原参 match。

### 用快照测试，保持配方稳定

新增配方测试快照的执行路径：先为每个测试项构造完整 Recipe 快照，调用现有 `recipe_render_request(info, snapshot, ...)` 规划，再复用现有串行出图和对照执行。

测试变体不通过 PUT 反复覆盖保存配方。run 关联原配方 id/版本，同时记录内容哈希、完整测试快照、素材 ref/exclusions 和最终请求指纹。角色与动作的语义替换仍由 Agent 完成或由用户在编辑器准备；后端校验结构、来源、参数与预览，不把简单堆词视为已正确替换。只在 Web 勾选素材、但尚未准备变体内容时，计划显示「待准备测试内容」，可复制对应 Agent 任务或手动编辑；不能把按钮描述成会自动启动一个未配置的外部 Agent。

因此批量测试不会产生恢复基准的并发问题，Web 仍能按原配方查看所有测试结果。这项属于第二阶段实施，不是第一阶段的前置依赖。

## 数据与 API 草案

文件放在各工作区已有 `data_dir` 中，继续使用当前 JSON 存储方式：

```text
custom_groups.json             # revision、组、主要成员、证据引用、锁定信息
analyses/<analysis_id>.json     # 输入快照、规则版本、Agent 判断和应用结果
test_plans/<plan_id>.json       # 选定配方、版本/内容哈希、素材快照、测试项、状态
recipes/<recipe_id>.json        # 原有配方存储
runs/<run_id>/                 # 原有出图、对照及新增快照字段
```

关键关系：

- `CustomGroup`：稳定 `id`、`parent_id`、名称/类型、备注、顺序、证据/来源、锁定信息；计数由成员计算，不让 Agent 手填汇总数字。
- `membership`：`image_id → leaf_group_id`，记录分组者与理由，使用文件级 revision 做乐观并发检查。
- `Recipe.source_group = {kind: custom|auto, id}`：明确组来源。旧 `group_id` 作为 legacy 自动组读取回退；新增代码统一经 group resolver 获取成员和统计，不再直接把任何 id 都放进自动分组中查。
- `Recipe.preparation`：分析 id、状态、代表源图指纹、建立配方时的分析依据。一个组可以被多个配方引用，列表反查，无需再保存一份 recipe_ids 真值。
- 新建自定义关系使用稳定 id；旧自动组因 id 可漂移，只作为旧数据兼容。自动组转自定义时固化成员，不长期依赖旧 `g1` 作为身份。

建议增加以下能力（路径均相对于 `/api/style-lab/workspaces/{w}`）：

| API | 用途 |
|---|---|
| `GET /analysis-context` | 分页读投稿、索引摘要、已有自定义组与人工锁定项 |
| `GET/PUT /custom-groups` | 读取/带 revision 保存组与归属，Web 与 Agent 共用校验 |
| `POST /preparations` | 接收 Agent 分析结果、建立分组和配方的操作计划；校验来源和版本，返回逐项应用结果 |
| `GET /preparations/{id}` | 恢复已保存分析及未完成建配方项 |
| `POST /test-plans` | 固化选中配方和素材快照、预览请求；不出图 |
| `POST /test-plans/{id}/start` | 显式提交测试；同一计划幂等启动 |
| `GET /test-plans/{id}` | 分项进度、已有结果复用、异常与实际出图数 |

`preparations` 是保存/应用当前 Agent 产生的结果，不代表后台自动启动外部 Agent。按组应用、记录操作 id 和结果：中断时已有分组可保留为「待建配方」，恢复只补未完成项；不能无记录地留下半完成结果或重复建配方。

现有 `/analyze` 继续用于 tag 分类/翻译与自动分组，不与新的准备流程共用含义。原有单图生图 API 继续提供，新的两阶段默认约定由 skill 与新入口执行。

## 重扫、编辑与恢复

- 新增图片先进入未分组，重扫不清空自定义组；再次分析针对新增/变化项提出建议。
- 源图缺失/元数据变化，标记受影响配方 source_missing/stale；重命名组或排序不会让配方失效。
- 修改分组不能隐式重写已有配方。需要重提取时明确产生更新建议或新的配方版本，已出图结果保留原快照。
- 删除组仅清理/调整关系，成员回到未分组；配方和历史保留并显示来源组已删除。删除父组需显式处理其子组关系，不能悬挂父引用。
- 分析和组保存检查 revision；配方沿用 version/updated_at 冲突保护。人工锁定不等于绕过并发检查。
- 测试计划开始前比对选定配方的完整内容哈希、源图指纹，而不能只比 version（主体修改不会增加画风版本）。发生变化时列差异、重建计划；不静默测试旧内容。开始后使用固定快照。
- 查重基于最终生成请求、源图/参考图指纹和结果存在性；同参成功结果复用。网络超时先查计划/run，失败或中断从未完成项恢复，不自动 force 重出整个批次。

## Skill 的调整

仍保留一个 `$style-lab`，在入口明确区分两种请求：

```text
$style-lab 整理这些文件夹，完成自定义分组和配方，暂不测试：...
$style-lab 测试工作区 w 的配方 r1、r2，使用当前选中的角色和动作。
```

默认「处理/整理这些图片」只做准备。没有明确测试请求时不生成；即便第一步建立了所有配方，也不能自动开始第二步。来源图库和既有风格 preset 保持只读。本项目引用的分析规则自包含，不修改 agent-hub 原 skill。

## 实施顺序与验收

**实施 A：完成第一步。** 自定义分组模型/校验/API → Web 切换、手动分组与详情 → typed group resolver 和配方关联 → 准备结果应用/恢复 → 迁移分析规则并更新 skill 默认行为。

**实施 B：完成第二步。** 组/配方多选 → 测试计划和出图数量预览 → 配方快照执行 → 批次恢复、复用和结果汇总 → skill 测试入口。

必须验证：

1. 多文件夹/散图完成准备后，工作区、自定义组、完整划分配方可见，生成 executor 调用次数为 0。
2. 无投稿信息时也能手建组；改名、合并、拆分、重扫、重启后归属正确且人工锁定不被重分析覆盖。
3. 自动组变化不会改变自定义组身份；配方共性、回归候选正确使用其来源类型。
4. 多图投稿、拆图和证据引用均不错误放大投稿占比；no_vibe/missing/特殊归档符合直接图片证据。
5. 只选 r1/r2 就只测试这些配方；共用源图原参去重；素材 exclusions 生效，每项种子和生成尺寸正确。
6. 测试不修改保存配方；准备状态和三类测试覆盖清楚区分。
7. 配方主体变化但画风版本不变时也能发现计划过期；超时/重启恢复不重复扣额度，失败/待处理原因可见。
